# ADR-010: เมื่อการต่อรองเนื้อหายังเหลือลิงก์มากกว่าหนึ่งรายการ

- **สถานะ:** Accepted
- **วันที่:** 2026-11-02
- **ผู้ตัดสินใจ:** ผู้วิจัย (ทบทวนกับอาจารย์ที่ปรึกษา)

## บริบท

หลังจากกรองด้วย `linkType`, `Accept`, และ `Accept-Language` แล้ว อาจยังเหลือลิงก์มากกว่าหนึ่งรายการ เช่น:
- สมาชิกลงทะเบียนหน้า product information สองภาษา (ไทย/อังกฤษ) แต่ผู้ใช้ไม่ส่ง `Accept-Language`
- มีลิงก์ `gs1:pip` สองรายการที่ต่างกันเล็กน้อย

GS1-Conformant Resolver Standard [4] §2.6.3 (ขั้นที่ 7 ของแนวทางที่แนะนำ) ระบุว่าเมื่อตัดสินไม่ได้ว่าลิงก์ใดตรงที่สุด resolver should ตอบรายการลิงก์ด้วย 300 Multiple Choices และตัวอย่างใน §2.7 ก็ตอบ 300 เมื่อประเภทลิงก์ตรงแต่ภาษาไม่ตรง GS1 Resolver CE ทำตามแนวทางนี้ (อ่านจาก `web_logic.py` ฟังก์ชัน `_handle_link_type`)

คำถาม: ระบบควรทำอย่างไรกับ candidate หลายรายการ?

## ทางเลือกที่พิจารณา

1. **เลือกหนึ่งรายการตาม heuristic แล้วเปลี่ยนเส้นทาง** ✓
   - ลำดับการเลือก: (1) คะแนน media type สูงสุด → (2) คะแนนภาษาสูงสุด → (3) ลำดับที่ลงทะเบียน
   - ข้อดี: browser/scanner ได้ผลทันที ไม่ต้องเลือกเพิ่ม

2. **ตอบ 300 Multiple Choices พร้อมรายการ URL**
   - ตรงกับแนวทางที่มาตรฐานแนะนำ (§2.6.3) และพฤติกรรมของ Resolver CE
   - ข้อเสีย: ผู้บริโภคที่สแกน QR ต้องเลือกลิงก์เอง แทนที่จะถูกพาไปหน้าเว็บทันที (พฤติกรรมของเบราว์เซอร์ต่อ 300 ต้องทดสอบยืนยันในขั้นตอน 7.7)

3. **ตอบ 200 พร้อม linkset JSON ทั้งหมด**
   - ให้ client เลือกเอง
   - ข้อเสีย: browser ที่รับ redirect จะได้ JSON blob แทน URL ที่ต้องการ

## พฤติกรรมของต้นแบบในปัจจุบัน

`src/pipeline/04_contentNegotiator.js` เรียง candidate ตาม:
1. คะแนน media type (จาก `q` parameter ใน Accept header)
2. คะแนนภาษา (จาก `q` parameter ใน Accept-Language header)
3. ลำดับที่ลงทะเบียนใน linkset (index ต่ำสุดได้ก่อน)

จากนั้นเลือก candidate แรกและส่งต่อให้ `05_responseBuilder.js` สร้าง 307 redirect

## หลักฐานที่ใช้ตัดสินใจ

| กรณีทดสอบ | เงื่อนไข | ต้นแบบ (รันจริง) | Resolver CE (คาดจากซอร์สโค้ด ยังไม่ได้รัน) |
|---|---|---|---|
| T-01 | ไม่มี Accept-Language, ลิงก์ปริยายมี 2 ภาษา | 307 → ลิงก์แรก (ไทย) | 300 Multiple Choices |
| กรณีเสริม (ยังไม่มีรหัส) | Accept-Language: th | 307 → URL ภาษาไทย | 307 → URL ภาษาไทย |
| T-07 | Accept-Language: en | 307 → URL ภาษาอังกฤษ | 307 → URL ภาษาอังกฤษ |

คาดว่า T-01 จะเป็นจุดที่พฤติกรรมต่างจาก CE ต้องยืนยันด้วยการรันในขั้นตอน 7.7

## การตัดสินใจ

**เลือกทางเลือกที่ 1:** เลือกหนึ่งรายการและ redirect

ผู้บริโภคที่สแกน QR code บนตัวสินค้าคาดหวังให้ถูกพาไปหน้าเว็บทันที ไม่ใช่ได้รับรายการตัวเลือก การตัดสินใจนี้เบี่ยงจากแนวทางที่มาตรฐานแนะนำใน §2.6.3 และต่างจาก Resolver CE โดยตั้งใจ ทั้งนี้แนวทางดังกล่าวใช้คำว่า should ในรายการแนวทางที่แนะนำ ไม่ได้เป็นข้อ SHALL ในหมวด 5 จึงไม่ถือเป็นการละเมิดข้อบังคับ แต่ต้องอภิปรายในวิทยานิพนธ์

## ผลที่ตามมา

**ข้อดี:**
- UX ดีสำหรับผู้บริโภคที่สแกน — ได้ redirect ทุกครั้ง
- ไม่ขึ้นกับ browser support ของ 300

**ข้อเสีย:**
- พฤติกรรมต่างจาก Resolver CE ใน T-01 — ต้องระบุและอธิบายความแตกต่างนี้ในวิทยานิพนธ์
- ข้อมูลบางส่วนสูญหาย (ลิงก์ที่ไม่ถูกเลือก) — client ไม่รู้ว่ามีตัวเลือกอื่น

**ข้อสังเกตจากมาตรฐาน:** §2.5.8 และหมวด 5 ข้อ 14 กำหนดให้มีลิงก์ปริยาย (`gs1:defaultLink`) เพียงลิงก์เดียวที่มี title และไม่มี attribute อื่น ส่วนรุ่นภาษาอื่นต้องใช้ `gs1:defaultLinkMulti` ข้อมูลตัวอย่างของต้นแบบยังมี `defaultLink` หลายรายการพร้อม hreflang และ type ซึ่งเป็นต้นเหตุของกรณีหลายลิงก์ใน T-01 ต้องแก้แบบจำลองข้อมูลก่อนสรุปผลเปรียบเทียบกับ CE

**ผลต่อ DPP:**
- เมื่อสินค้ามีใบรับรองหลายฉบับใน `gs1:certificationInfo` ต้นแบบพาไปฉบับแรก (DPP-05 ใน `demo.sh`) ผู้ที่ต้องการทุกฉบับต้องขอชุดลิงก์ ถ้าเปลี่ยนเป็น 300 ตาม §2.6.3 ผู้เรียกจะเห็นรายการให้เลือก

**สิ่งที่ต้องทำต่อ:**
- แก้แบบจำลองข้อมูลให้แยก `gs1:defaultLink` (ลิงก์เดียว) กับ `gs1:defaultLinkMulti` ตาม §2.5.8
- เพิ่ม `Link` header บอก alternate URL เมื่อมี candidate หลายรายการ เช่น `Link: <url2>; rel="alternate"; hreflang="en"`
- อธิบายความแตกต่างจาก CE ในบท Discussion ของวิทยานิพนธ์ว่าเป็น intentional design choice
