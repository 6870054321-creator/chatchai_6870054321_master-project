# ADR-001: ตำแหน่งของการตรวจสอบตัวระบุ

- **สถานะ:** Accepted
- **วันที่:** 2026-11-02
- **ผู้ตัดสินใจ:** ผู้วิจัย (ทบทวนกับอาจารย์ที่ปรึกษา)

## บริบท

ระบบต้องตรวจสอบความถูกต้องของตัวระบุ GS1 ใน 2 มิติ:
1. **ไวยากรณ์และ checksum** — ตรวจด้วยอัลกอริทึม Mod-10 (GS1 General Specifications §7.9)
2. **ช่วงเลขบ่งชี้บริษัท** — ตรวจว่า GCP prefix อยู่ใน `ALLOWED_PREFIXES` ที่สถาบันรับผิดชอบหรือไม่ คือ 885

ระบบมีสองเส้นทางที่รับตัวระบุ:
- **เส้นทางอ่าน (Read path):** ท่อประมวลผล 5 ขั้นตอน — Stage 2 คือ `validator.js`
- **เส้นทางเขียน (Write path):** Link Ingest API — `ingestApi.js`

คำถามคือควรวางตรรกะตรวจสอบไว้ที่จุดใดจึงจะมีประสิทธิภาพและปลอดภัยที่สุด

## ทางเลือกที่พิจารณา

1. **ตรวจที่เส้นทางอ่านเท่านั้น (Stage 2)**
   - ข้อดี: เส้นทางเขียนเบาลง สามารถนำเข้าข้อมูลจาก legacy ได้ทุกรูปแบบ
   - ข้อเสีย: ข้อมูลเสียเข้า store ได้ ส่งผลต่อผู้ใช้ทุกคนที่ query GTIN นั้น

2. **ตรวจที่เส้นทางเขียนเท่านั้น (Ingest API)**
   - ข้อดี: กรองที่ต้นทาง ข้อมูลใน store ถูกต้องทั้งหมด
   - ข้อเสีย: เส้นทางอ่านยังเปิดรับตัวระบุที่เข้า store จากช่องทางอื่น (เช่น load ไฟล์ JSON โดยตรง)

3. **ตรวจทั้งสองเส้นทางด้วยโมดูลเดียวกัน** ✓
   - `src/pipeline/validator.js` ถูกเรียกจากทั้ง Stage 2 และ `ingestApi.js`
   - ข้อดี: single source of truth ป้องกันทั้งการเขียนข้อมูลเสียและการ query ด้วยตัวระบุที่ไม่ถูกต้อง

## พฤติกรรมของต้นแบบในปัจจุบัน

`src/pipeline/validator.js` ถูก import และเรียกใช้จากทั้ง `src/app.js` (Stage 2) และ `src/ingest/ingestApi.js` ทำให้กฎการตรวจสอบอยู่ที่โมดูลเดียว การแก้ไขกฎ (เช่น เพิ่ม prefix ใหม่) มีผลทั้งสองเส้นทางทันที

## หลักฐานที่ใช้ตัดสินใจ

| กรณีทดสอบ | สิ่งที่ตรวจ | ผลที่คาดหวัง |
|---|---|---|
| T-10 | GTIN checksum ไม่ถูกต้อง (Mod-10 fail) | 400 (เส้นทางอ่าน) / 422 (Link Ingest API) |
| T-11 | GTIN ถูกต้องแต่อยู่นอก ALLOWED_PREFIXES | 404 (เส้นทางอ่าน) / 422 (Link Ingest API) |
| T-12 | GTIN-13 ถูกแปลงเป็น GTIN-14 ก่อนตรวจ | ได้ผลเดียวกับ T-01 และเก็บด้วยกุญแจ 14 หลักเมื่อนำเข้า |
| S-02 | AI 17 (ข้อมูลประกอบ) อยู่ใน path | 400 (เส้นทางอ่าน) / 422 (Link Ingest API) |
| Unit test | `identifier rules are shared with stage 2` | test ผ่านทั้งสองเส้นทาง |

## การตัดสินใจ

**เลือกทางเลือกที่ 3:** ตรวจสอบทั้งสองเส้นทางด้วย `validator.js` โมดูลเดียว

GS1-Conformant Resolver Standard [4] §2.4 ระบุว่าข้อมูลควรถูกตรวจตั้งแต่ตอนนำเข้า ("it SHOULD be impossible to register a link against an invalid GS1 identifier") และรีโซลเวอร์ยังต้องตรวจขั้นพื้นฐานก่อนค้นลิงก์ ส่วน §2.4.1 และหมวด 5 ข้อ 7 กำหนดให้ตอบ 400 เมื่อ URI ไม่ผ่านการตรวจ การใช้ validator โมดูลเดียวทำให้เส้นทางอ่านและเขียนใช้กฎชุดเดียวกัน ลดความเสี่ยงที่กฎสองชุดจะต่างกันเมื่อเพิ่มกุญแจหลักใหม่ในอนาคต

## ผลที่ตามมา

**ข้อดี:**
- กฎการตรวจสอบอยู่ที่เดียว แก้ครั้งเดียวมีผลทั้งระบบ
- T-10, T-11 ผ่านทั้งเส้นทางอ่านและเขียน
- รองรับการเพิ่ม primary key ใหม่ได้ง่าย (แก้เฉพาะ `validator.js`)

**ข้อเสีย:**
- มี overhead ในเส้นทางอ่าน แต่น้อยมาก (Mod-10 = O(n) บน 14 หลัก, < 1 µs)

**สิ่งที่ต้องทำต่อ:**
- เมื่อเพิ่ม primary key ใหม่ (เช่น SSCC, GLN) ต้องเพิ่มกฎใน `validator.js` พร้อม test cases ที่สอดคล้อง
